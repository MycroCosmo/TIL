# 조건부 UPDATE로 결제 중복 통보 한 번만 반영하기

> 작성일: 2026-11-19

## 한 줄 요약

같은 결제 결과가 여러 번 들어와도 **상태 조건을 건 UPDATE 한 번**으로 처리하면, 영향받은 행 수로 "처음 온 것인지"를 판별할 수 있다.

## 내용

### 상황

- PG사의 결제 결과는 브라우저 리다이렉트와 서버 웹훅으로 **여러 번** 들어올 수 있다.
- 반대로 승인 응답이 네트워크 문제로 **누락**될 수도 있다.
- 같은 결제를 두 번 반영하면 주문이 중복 처리되고, 누락되면 돈은 나갔는데 주문이 안 된다.

### 검토한 방법

| 방법 | 판단 |
| --- | --- |
| 조회 후 확인 (`SELECT` 후 상태가 READY면 처리) | 두 요청이 동시에 READY를 볼 수 있어서 탈락 |
| 비관적 락 | 확실하지만 대기와 데드락 부담 |
| **조건부 UPDATE** | 쿼리 하나로 원자적, 영향 행 수로 중복 판별 → 선택 |

### 구현

```sql
UPDATE payment
SET status = 'PAID', paid_at = NOW()
WHERE payment_id = #{paymentId}
  AND status = 'READY'
```

```java
int updated = paymentMapper.markPaid(paymentId);
if (updated == 0) {
    // 이미 처리된 통보 → 아무것도 하지 않고 성공 응답
    return;
}
// 처음 반영된 경우에만 후속 처리
```

- 두 번째 요청은 `status = 'READY'` 조건에 걸려 0건이 되므로 자연스럽게 무시된다.
- 웹훅에는 이미 처리했더라도 **성공 응답**을 준다. 실패로 응답하면 PG사가 계속 재전송한다.

### 응답 누락 대비

- 승인 응답을 못 받았으면 PG사의 **결제 조회 API로 실제 결제 상태를 다시 확인**한다.
- 확정하지 못한 건은 별도 상태로 남겨두고, 배치에서 다시 조회해 정리한다.

## 헷갈렸던 점 / 주의할 점

- 멱등성은 "여러 번 실행해도 결과가 같다"는 뜻이다. HTTP에서 GET·PUT·DELETE는 멱등, POST는 멱등이 아니다.
- 배치가 중간에 멈춰도 다시 돌렸을 때 **남은 건부터** 처리되게 건 단위로 상태를 저장하면, 배치도 멱등하게 만들 수 있다.
- 미확정 건을 하루 한 번 배치로만 정리하면 확정이 최대 하루 늦어질 수 있다. 짧은 주기로 재조회하는 작업을 따로 두는 방법도 있다.
