# 저장 프로시저를 MyBatis로 이관한 뒤 생긴 타임아웃

> 작성일: 2026-11-19

## 한 줄 요약

SQL Server 저장 프로시저 로직을 MyBatis 쿼리 하나로 옮기면서 조회가 무거워져 20초 타임아웃이 났다. **실행계획을 보고 쿼리를 단계로 나누고, 운영에서는 파라미터 스니핑을 `OPTION (RECOMPILE)`로 해결**했다.

## 상황

- 레거시 시스템을 Spring Boot + MyBatis로 이관하는 작업.
- 프로시저 안에서 여러 단계로 나눠 처리하던 조회를 애플리케이션 SQL 하나로 옮겼다.
- 조회 기간을 길게 잡으면 20초 쿼리 타임아웃이 발생했다.

## 원인 분석

1. **실행계획 확인**: 행마다 반복 실행되는 상관 서브쿼리가 원인 중 하나였다.
2. **단계가 사라짐**: 프로시저에서는 중간 결과를 나눠 담으며 처리했는데, 쿼리 하나로 합치면서 큰 조인이 한 번에 생겼다.
3. **운영에서만 다시 느려짐**: 같은 쿼리가 개발 서버에서는 개선됐는데 운영에서 다시 타임아웃이 났다. 캐시된 실행계획이 운영의 파라미터·데이터 분포와 맞지 않았다(파라미터 스니핑).

## 해결

- 상관 서브쿼리 대신 **미리 집계한 결과와 조인**하도록 바꿨다.
- 중간 결과를 **임시 테이블**에 나눠 담았다. 임시 테이블은 통계 정보를 가져서 옵티마이저가 단계별로 더 나은 계획을 세울 수 있다.
- 조건 컬럼의 **인덱스**를 확인했다.
- 운영 문제는 `OPTION (RECOMPILE)`로 실행할 때마다 실제 파라미터 기준으로 계획을 만들게 했다. 호출 빈도가 낮고 조회가 무거운 쿼리라 컴파일 비용보다 잘못된 계획의 비용이 훨씬 컸다.

결과: 20초 타임아웃이 나던 쿼리를 개발 서버 기준 약 5초로 줄였다.

## 배운 점

- 프로시저 → 애플리케이션 SQL 이관은 **문법 변환이 아니라 실행 방식의 변화**다. 프로시저가 단계를 나눠 처리하던 이유가 있었다.
- 개발과 운영의 데이터 분포가 다르면 같은 쿼리도 다른 계획을 탄다. 개발 서버에서 빠르다고 끝난 게 아니다.
- 프로시저와 애플리케이션 SQL의 차이
  - 프로시저: DB 안에서 왕복 없이 처리, 대신 버전 관리·테스트가 어렵다.
  - 애플리케이션 SQL: 코드와 함께 관리되지만 왕복 횟수와 트랜잭션 경계를 직접 설계해야 한다.
